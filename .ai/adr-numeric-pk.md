# Numeric Primary Keys Assigned by the Application

## Context
String or UUID primary keys (e.g. `VARCHAR(32)` populated with a UUID) use more storage,
produce larger indexes, cause random index fragmentation, and are slower to compare than
integers. Assigning the key in the application layer (rather than via a database
auto-increment sequence) gives the application control of the ID before the record is
persisted, which simplifies parent-child inserts.

## Decision
Every table must have a numeric primary key (`BIGINT`) named `id`, populated by the
application layer before the record is written to the database.

## Compliance Levels
- **Non-compliant**: UUID or string primary keys generated by the database or ORM.
- **Partial**: New tables use numeric keys; existing legacy tables retain string keys temporarily.
- **Compliant**: All tables use application-assigned numeric primary keys.

## Examples

### Preferred
```sql
CREATE TABLE account (
    id              BIGINT          PRIMARY KEY,
    external_id     VARCHAR(50)     NOT NULL,
    currency_code   VARCHAR(3)      NOT NULL
    -- ...
);
```

```java
public class Account {
    private final Long id;

    public Account(...) {
        this.id = IdSupport.nextId(); // TSID or similar — assigned before DB write
        // ...
    }
}
```

### Not Allowed
```sql
-- String/UUID primary key
CREATE TABLE account (
    id VARCHAR(36) PRIMARY KEY DEFAULT (UUID())
    -- ...
);
```

```java
// Key generated by the ORM / database — application has no ID until after the INSERT
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```
